================================================================================
ONTOQUORUM — Comprehensive draw.io Build Guide for the End-to-End System Diagram
================================================================================

System name: ONTOQUORUM
Backronym (optional): Ontology-Grounded Forging of Knowledge Graphs from
                      Scientific Tables
Tagline:    "Ontology as the anvil. Five parsers as the hammer."

This guide walks through every component of the end-to-end system, drawn
on the geochemistry instantiation (the most complete code path — uses
all 5 backends, both supp + PDF inputs, deposit classification, validator,
and the graph builder). Other domains (ChemTables, MLTables, DiSCoMaT) are
shown as ontology-swap chips at the bottom rather than redrawn.

================================================================================

A reader scanning the figure for 5 seconds should leave with FOUR
impressions:

1. HORIZONTAL PIPELINE going left-to-right through 8 columns.
2. THE GOLD HEXAGON at the bottom is the central character, with
   six dashed arrows shooting UP into the pipeline stages — this
   is the "ontology = first-class" thesis made visual.
3. THE 5-BACKEND STACK in Column 3 communicates "many parsers
   reconciled" without listing each by name unnecessarily.
4. THE FOUR CHIPS at the very bottom communicate "domain-adaptable
   without code change."

If those four things don't land in 5 seconds, simplify until they do.

Specifically — if any column is visually heavier than the gold hexagon,
that column has stolen the thesis. Reduce its border weight or shrink
its size.

15. FALLBACK CASCADE — THE HIDDEN ARCHITECTURAL HERO  (READ THIS BEFORE DRAWING)
================================================================================

The original guide above treats the multi-extractor block (Col 3) and the
supp / PDF inputs as if they fire in parallel. That is misleading. The
real architecture is a TIERED FALLBACK CASCADE: each tier is tried only
if the previous tier under-produces. This is how the system stays
high-precision when supp files exist AND high-recall on PDF-only papers,
without doubling cost on common cases.

Render the cascade EXPLICITLY. Here is the redesign:

------------------------------------------------------------
15.1  THE FIVE-LAYER EXTRACTION CASCADE
------------------------------------------------------------

Cascade layer    | What it does                            | Cost  | Fires when
-----------------+----------------------------------------+-------+-------------
Layer 0: SUPP    | Deterministic XLSX/CSV parser           | $0   | supp file
                 | (Stage 2a)                              |       | exists
-----------------+----------------------------------------+-------+-------------
Layer 1: DIRECT  | Read numbers straight from extracted    | $0   | tables
                 | DataFrames (no LLM call)                |       | found by any
                 | (Stage 2b-1)                            |       | of 5 backends
-----------------+----------------------------------------+-------+-------------
Layer 2: SELF-   | Agentic diagnostic LLM emits            | $$   | Layer 1
        CORRECT  | ParsingHints; retry Layer 1             |       | under-extracted
                 | (Stage 2b-1.5; max 2 attempts)          |       | (n_rows below
                 |                                         |       | DocIntel
                 |                                         |       | expectation)
-----------------+----------------------------------------+-------+-------------
Layer 3: LLM     | Per-table LLM extraction from           | $$$  | Layer 1+2
                 | table-text strings                      |       | still under
                 | (Stage 2b-2)                            |       | expectation
-----------------+----------------------------------------+-------+-------------
Layer 4: VISION  | Page-image extraction via vision LLM    | $$$$ | Layer 3
                 | on data-dense page images               |       | found 0 rows
                 | (Stage 2b-3)                            |       | OR text
                 |                                         |       | backends found
                 |                                         |       | 0 tables
-----------------+----------------------------------------+-------+-------------
Layer 5: TEXT-   | Raw-text-only fallback (data pages or   | $$   | All previous
        ONLY     | full PDF text)                          |       | layers failed
                 | (Stage 2b-4)                            |       |
-----------------+----------------------------------------+-------+-------------

Plus completeness gate (Stage 2b-5):
  AFTER all layers, if total extracted samples < ~50 % of expected
  count from DocIntel, the pipeline marks the paper as "partial" and
  surfaces the underrun in run-log telemetry.

Plus merge precedence (Stage 2c):
  If both supp and PDF tiers produced rows, the merger uses
  SUPP wins on numerical values, PDF wins ONLY for samples NOT
  present in supp. This is a fallback IN REVERSE: PDF rescues
  what supp doesn't cover.
